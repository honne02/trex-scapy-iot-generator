# IoT Traffic Generation Node

Программный комплекс для генерации специфического трафика Интернета вещей (IoT) на базе Cisco TRex и Scapy. Разработано в рамках дипломного проекта по теме: "Разработка узла генерации трафика на модельной сети".

## Описание проекта

Данный узел позволяет имитировать работу сотен IoT-устройств (датчиков), передающих данные по протоколу CoAP (Constrained Application Protocol). Основное отличие от стандартных генераторов — возможность гибкого конструирования L2/L3/L7 заголовков для создания реалистичного профиля нагрузки.

### Технологический стек

- **Генератор:** Cisco TRex v3.08 (Stateless Mode)
- **Packet Builder:** Scapy (Python 3)
- **Среда:** Ubuntu Server 24.04 / Proxmox VE
- **Технологии:** DPDK, Virtualization, Traffic Engineering

## Архитектура решения

Система построена по принципу разделения Control Plane и Data Plane:

1. **Management Interface:** Управление и SSH
2. **Data Interface:** Выделенный порт для инжекции трафика (используется программная эмуляция `--software` для отладки и DPDK для продакшн-сервера)

## Установка и настройка

### Автоматическая установка

Скрипт `setup_generator_trex_IoT.sh` автоматически выполнит:
- Установку зависимостей (Python3, Scapy, tcpdump, ethtool)
- Загрузку и установку Cisco TRex
- Настройку сетевого интерфейса
- Генерацию конфигурационного файла `/etc/trex_cfg.yaml`

Запуск установки:

```bash
sudo bash setup_generator_trex_IoT.sh
```

В процессе установки необходимо:
1. Выбрать сетевой интерфейс для генерации трафика
2. Выбрать режим работы:
   - **Lab Mode** (Software emulation) - для тестирования и отладки
   - **Combat Mode** (DPDK) - для продакшн-сервера с прямым доступом к железу

### Использование сценариев с TRex

Все stateless-сценарии генерируют PCAP-файл в `/tmp/iot_traffic.pcap`, который можно передать в TRex для воспроизведения. 

```bash
# Генерируем трафик сценария
python3 scenarios/iot_coap_sensors.py aa:bb:cc:dd:ee:ff

# В консоли TRex запускаем воспроизведение
push -f /tmp/iot_traffic.pcap -p 0 --force
```

Можно использовать разные сценарии для различных тестовых случаев:
- **CoAP** для тестирования IoT-сенсоров
- **MQTT** для тестирования подписочных сервисов
- **Modbus/TCP** для тестирования критичного промышленного трафика
- **OTA** для тестирования высоконагруженного трафика обновлений
- **ASTF HTTP** для тестирования stateful HTTP трафика и DPI верификации
- **Двусторонняя нагрузка** для тестирования asymmetric трафика (uplink/downlink)
- **RFC 2544 Benchmark** для измерения Latency/Jitter под нагрузкой

## Запуск генератора

Для работы генератора требуется два терминала или интегрированный запуск через setup скрипт.

### Быстрый запуск через Setup скрипт

Рекомендуемый способ с автоматической подготовкой PCAP файлов и конфигурацией:

```bash
sudo bash setup_generator_trex_IoT.sh
```

Скрипт интерактивно:
1. Выберет режим (только генерация или полная установка)
2. Сканирует сетевые интерфейсы
3. Позволит выбрать один или два интерфейса для генерации трафика
4. Предложит выбрать сценарий или тест
5. Автоматически сгенерирует PCAP файл и установит правильные права доступа
6. Выведет команды для запуска в TRex

### Ручной запуск (два терминала)

### Терминал 1: Запуск TRex сервера

```bash
cd /opt/trex/v3.08
sudo ./t-rex-64 -i --software
```

Параметры:
- `-i` - интерактивный режим
- `--software` - программная эмуляция (для Lab Mode)

### Терминал 2: Консоль управления

```bash
cd /opt/trex/v3.08
./trex-console
```

В консоли TRex доступны два варианта запуска:

```
# Вариант А: Одиночный выстрел (проверка связности и счетчиков)
push -f /tmp/iot_traffic.pcap -p 0 --force

# Вариант Б: Непрерывный шторм (бинарный поиск пропускной способности)
start -f ./scenarios/throughput_profile.py -p 0 -m 10%
```

Параметры:
- `-f` - путь к PCAP-файлу
- `-p 0` - номер порта (0 - первый интерфейс)
- `--force` - принудительный запуск

## Готовые сценарии IoT-трафика

В папке `scenarios/` содержатся готовые к использованию сценарии для генерации различных типов IoT-трафика. Каждый сценарий может быть запущен независимо для создания соответствующего PCAP-файла.

### Сценарий 1: CoAP датчики (iot_coap_sensors.py)

**Описание:** Имитация сбора данных с сенсорного поля (100 датчиков) по протоколу CoAP.

**Характеристики:**
- **Количество устройств:** 100
- **Протокол:** CoAP over UDP (порт 5683)
- **IP-адреса источников:** 10.0.0.1 - 10.0.0.100
- **IP-адрес назначения:** 192.168.1.100
- **MAC-адреса:** Уникальные для каждого пакета (RandMAC) - имитация разных датчиков
- **Payload:** Телеметрия датчиков (temp=22)
- **Использование:** Тестирование нагрузки на шлюз, анализ поведения при большом количестве источников

**Запуск:**
```bash
python3 scenarios/iot_coap_sensors.py <MAC-адрес>
```

---

### Сценарий 2: MQTT телеметрия (iot_mqtt_telemetry.py)

**Описание:** Имитация MQTT-телеметрии от распределенных умных устройств к центральному брокеру.

**Характеристики:**
- **Количество устройств:** 50
- **Протокол:** MQTT over TCP (порт 1883)
- **IP-адреса источников:** 10.0.1.1 - 10.0.1.50
- **IP-адрес назначения:** 192.168.1.100
- **Payload:** MQTT CONNECT пакет с идентификатором устройства
- **Использование:** Анализ стабильности сессий, тестирование длительного подключения

**Запуск:**
```bash
python3 scenarios/iot_mqtt_telemetry.py <MAC-адрес>
```

---

### Сценарий 3: Modbus/TCP промышленность (iot_industrial_modbus.py)

**Описание:** Имитация промышленного трафика (Modbus/TCP) для мониторинга состояния контроллеров (ПЛК) в индустриальных сетях (IIoT).

**Характеристики:**
- **Количество контроллеров:** 30
- **Протокол:** Modbus/TCP (порт 502)
- **IP-адреса источников:** 10.0.2.1 - 10.0.2.30
- **IP-адрес назначения:** 192.168.1.100
- **TCP-порты:** 502 → 502
- **Функция:** Read Holding Registers (Function Code 3)
- **Payload:** MBAP Header + PDU `Read Holding Registers` с начальным адресом `0`, чтением `10` регистров и 10 байтами padding, чтобы полезная нагрузка была больше 16 байт для TRex Latency
- **MAC-адрес:** Можно передать явно; если аргумент не указан, используется `00:00:00:00:00:00`
- **Использование:** Тестирование критичного промышленного трафика, анализ задержек

**Запуск:**
```bash
python3 scenarios/iot_industrial_modbus.py [MAC-адрес]
```

### Сценарий 4: OTA обновления (iot_firmware_update.py)

**Описание:** Моделирование процесса обновления ПО (OTA Update) с передачей крупных блоков данных от сервера к устройствам.

**Характеристики:**
- **Количество устройств:** 50
- **Протокол:** HTTP over TCP (порт 8080 → 80)
- **IP-адреса назначения:** 10.0.0.1 - 10.0.0.50
- **IP-адрес источника:** 192.168.1.100
- **Payload:** Блоки данных прошивки (FIRMWARE_DATA_BLOCK_XXX...)
- **Использование:** Тестирование высокого трафика вверх по ссылке, анализ поведения при больших передачах

**Запуск:**
```bash
python3 scenarios/iot_firmware_update.py <MAC-адрес>
```

### Сценарий 5: Комбинированный стресс-тест (iot_combined_stress_test.py)

**Описание:** Одновременная эмуляция 150 устройств (CoAP + MQTT) для проверки шлюза при экстремальной нагрузке и NAT/ARP обработке в соответствии с Q.3900 Уровень 2.2.

**Характеристики:**
- **Количество устройств:** 150 (100 CoAP + 50 MQTT)
- **CoAP датчики:**
  - Протокол: CoAP over UDP (порт 5683)
  - IP-адреса источников: 10.0.0.1 - 10.0.0.100
  - Payload: Телеметрия (temp=22)
- **MQTT устройства:**
  - Протокол: MQTT over TCP (порт 1883)
  - IP-адреса источников: 10.0.1.1 - 10.0.1.50
  - Payload: MQTT CONNECT пакет с идентификатором устройства
- **IP-адрес назначения (общий):** 192.168.1.100
- **MAC-адреса:** Уникальные для каждого пакета (RandMAC) - максимальная эмуляция реальности
- **Использование:** Комплексное тестирование шлюза под экстремальной нагрузкой, валидация NAT/ARP механизмов, проверка поведения при одновременном использовании разных протоколов

**Запуск:**
```bash
python3 scenarios/iot_combined_stress_test.py <MAC-адрес>
```

### Сценарий 6: ASTF HTTP IoT (iot_stateful_http.py)

**Описание:** Эмуляция stateful HTTP-трафика с полным TCP handshake и L7 (Application Layer) взаимодействием между 255 IoT-клиентами и центральным сервером. Использует TRex ASTF API для создания реалистичного трафика с полным жизненным циклом сессии.

**Характеристики:**
- **Количество клиентов:** 255
- **Протокол:** TCP HTTP (порт 80)
- **IP-адреса источников (клиенты):** 16.0.0.1 - 16.0.0.255
- **IP-адрес назначения (сервер):** 48.0.0.1
- **HTTP запрос:** GET /config.json (реалистичный URL для IoT конфигурации)
- **HTTP ответ:** 200 OK с JSON-телом `{"status":"ok"}`
- **Особенности:** 
  - Полный TCP handshake (SYN, SYN-ACK, ACK)
  - Realtime L7 взаимодействие (запрос-ответ)
  - Verifikacija DPI (Deep Packet Inspection)
- **Использование:** Тестирование stateful трафика, проверка HTTP парсеров, анализ L7-фильтрации, верификация DPI-обработчиков

**Запуск с TRex:**
```bash
# Метод 1: Использование TRex CLI
cd /opt/trex/v3.08
./trex-console
tui    # или запуск профиля напрямую
start -f /path/to/iot_stateful_http.py -m 1 -d 10

# Метод 2: Прямой запуск через Python API
python3 -c "
import sys
sys.path.append('/opt/trex/v3.08/automation/trex_control_plane/interactive')
from trex.astf.trex_astf_client import ASTFClient

client = ASTFClient()
client.connect()
client.load_profile('/path/to/iot_stateful_http.py')
client.start(duration=10)
client.wait_on_traffic()
client.disconnect()
"
```

Параметры:
- `-f` - путь к профилю Python
- `-m` - множитель нагрузки (1 = база, 2 = двойная нагрузка)
- `-d` - длительность теста в секундах

### Сценарий 7: Двусторонняя Нагрузка (iot_load_bidirectional.py)

**Описание:** Эмуляция реальной IoT-сети с asymmetric трафиком - одновременная отправка данных от датчиков (uplink) и получение ответов/обновлений от сервера (downlink). Каждый датчик получает уникальный случайный MAC-адрес для максимально реалистичной эмуляции.

**Характеристики:**
- **Uplink (датчики → сервер):**
  - 100 CoAP датчиков (UDP)
  - Порт: 5683
  - IP-адреса источников: 10.0.0.1 - 10.0.0.100
  - Размер пакета: 64 байта
  - MAC-адреса: Уникальные случайные для каждого датчика (RandMAC)
- **Downlink (сервер → датчики):**
  - 50 TCP соединений (асимметричный ответ)
  - Порт: 8080 → 80
  - Размер пакета: 1058 байта (HTTP нагрузка)
  - IP-адреса назначения: 10.0.0.1 - 10.0.0.50
- **IP-адрес сервера:** 192.168.1.100
- **Итого пакетов:** 150 (100 uplink + 50 downlink)
- **Использование:** Тестирование обработки asymmetric нагрузки, проверка буферов Rx/Tx, анализ поведения при одновременной передаче и приеме, отработка механизмов ARP/MAC-learning

**Запуск:**
```bash
python3 scenarios/iot_load_bidirectional.py aa:bb:cc:dd:ee:ff
```

Сценарий поддерживает запуск в режиме `--dual` TRex для оптимальной обработки двусторонней нагрузки на двух портах.

## Тесты Производительности (Benchmarks)

Папка `benchmarks/` содержит специализированные тесты для измерения производительности и качества обслуживания (QoS).

### TRex Throughput Profile (throughput_profile.py)

**Описание:** Профиль-обертка для TRex, обеспечивающая непрерывную циклическую генерацию PCAP-файлов в режиме STLTXCont для поиска максимальной пропускной способности (Throughput) по методике RFC 2544.

**Характеристики:**
- **Режим:** STLTXCont (Stateless Continuous Transmission)
- **Источник трафика:** `/tmp/iot_traffic.pcap` (автоматически генерируется сценариями)
- **Использование:** Нахождение максимальной пропускной способности канала под заданной нагрузкой
- **Метрики:** Throughput (Мбит/с), TX/RX packets, latency

**Запуск в TRex консоли:**
```bash
# Загрузить профиль и запустить
start -f /path/to/scenarios/throughput_profile.py -m 1 -d 60

# -f   путь к профилю Python
# -m   множитель нагрузки (1 = базовый)
# -d   длительность теста в секундах
```

---

### RFC 2544 Latency Benchmark (latency_test_rfc2544.py)

**Описание:** Автоматизированный измеритель задержки (latency) и вариабельности (jitter) согласно методике RFC 2544. Тест использует две фазы: стабилизация (60 сек) + измерение (60 сек).

**Характеристики:**
- **Фаза 1 (Разминка):** 60 сек - стабилизация очередей и ARP кэша
- **Фаза 2 (Измерение):** 60 сек - чистый замер метрик после сброса счетчиков
- **Нагрузка:** 2 потока на порту 0:
  - Фоновый трафик (50% канала): Двусторонняя Нагрузка (iot_load_bidirectional.py)
  - Контрольный поток: Modbus/TCP для измерения Latency/Jitter
- **Метрики:**
  - Average Latency (средняя задержка)
  - Max/Min Latency (пиковые значения)
  - Jitter (вариабельность)
  - RX packet count (кол-во полученных пакетов)

**Требования:**
```bash
# Сначала сгенерируй PCAP файлы для нагрузки
python3 scenarios/iot_load_bidirectional.py aa:bb:cc:dd:ee:ff
# Сохранить копию с именем фонового трафика
cp /tmp/iot_traffic.pcap /tmp/iot_bg_load.pcap

# Потом сгенерируй контрольный поток Modbus
python3 scenarios/iot_industrial_modbus.py aa:bb:cc:dd:ee:ff
# Сохранить копию под именем контрольного трафика
cp /tmp/iot_traffic.pcap /tmp/iot_modbus.pcap

# Потом запусти benchmark
python3 benchmarks/latency_test_rfc2544.py
```

**Интерпретация Результатов:**
- ✅ **Average Latency < 10 мс** → отлично
- ⚠️ **Average Latency 10-20 мс** → приемлемо
- ❌ **Average Latency > 20 мс** → проблема, требует оптимизации
- ✅ **Jitter < 5 мс** → стабильная сеть
- ❌ **Jitter > 10 мс** → нестабильность

## Устранение неполадок

### Интерфейс не поднимается

Проверьте состояние линка:

```bash
cat /sys/class/net/<interface>/operstate
ip link set <interface> up
```

### TRex не видит интерфейс

Проверьте конфигурацию:

```bash
cat /etc/trex_cfg.yaml
```

Убедитесь, что PCI-адрес или имя интерфейса указаны корректно.

### Ошибка при запуске в Combat Mode

Убедитесь, что:
- Интерфейс не используется другими процессами
- Драйвер поддерживает DPDK
- Модули DPDK загружены
